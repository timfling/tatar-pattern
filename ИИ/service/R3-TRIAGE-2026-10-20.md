## Фактическая граница runtime

- `workflow.validate` допускает ровно 9 полей: contractVersion, workflowVersion,
  modelVersion, catalogVersion, baseId, baseSha256, ornamentStyle, profileVersion,
  seed (целое 0…2147483647). Лишние поля отвергаются. Prompt, strength, steps,
  размеры и пути берутся из серверного реестра. Upload/model URL/custom pipeline нет.
- `render_one.main` до inference вызывает `deployment(config)` и `resolved`,
  проверяет 9 версий; затем использует конкретный
  `StableDiffusionXLImg2ImgPipeline.from_pretrained(snapshot_path, variant='fp16',
  use_safetensors=True, local_files_only=True)`. LoRA тоже только local safetensors.
  Нет training/Trainer, conversion, custom_generate, save_pretrained, pt2 loader.
- База: официальный SDXL repo и revision
  `462165984030d82259a11f4367a4eed129e94a7b`; SHA всех 22 перечисленных файлов
  (включая model_index/config/tokenizers) проверяются перед загрузкой. В inventory
  нет `.py`, pickle или sharded weight_map index. LoRA SHA
  `378c08ff157660a3399573e1cd5918ad8f3aec344646c5336b027d63fe50ca42`.
- `deployment` проверяет SHA исходного PNG **до** Image.open/load, затем PNG/RGB/1024²;
  render повторно сверяет SHA. Выход всегда RGB PNG. Нет координат, шрифтов,
  фильтров или выбора формата из HTTP. PNG результата читает также server.py.
- Эти исключения действуют при доверенных operator-managed config/inventory/assets
  и неизменном коде. SHA-проверка покрывает перечисленные файлы, **не** exact file set
  всего snapshot и не права записи. `local_files_only` сам по себе не запрещает
  локальный custom code; safetensors не проверяет безопасность произвольного config.
  Права/egress/лишние файлы на живой ВМ сейчас NOT_RUN. При изменении этой границы
  исключения пересматриваются до допуска задач.

## Реестр применимости

«Неприменимо» означает отсутствие условий именно в данном runtime, а не исправление
самой библиотеки. Три «ограничения» Torch сохраняют неопределённость коротких OSV
описаний и непроверенных внутренних вызовов; они не означают доказанный exploit
через seed. Версионные диапазоны приняты из OSV, даже когда details приводят пример
на другой версии. Алиасы в одной строке считаются одной уязвимостью.

## Решение и точный handoff deploy-агенту через владельца

**GPU-код, pins, VERSIONS, профили и веса не изменены.** Изменены только review evidence
в собственной GPU-зоне и собственный summary. Из этого разбора не следует необходимость
перестраивать GPU runtime или делать новые платные генерации. Принятые ограничения:
только данный SDXL путь/серверный реестр/локальные доверенные SHA assets; без внешних
моделей, custom components, upload, pickle/checkpoint conversion. Не включать эти
возможности, ссылаясь на нынешние исключения.

Точная GPU-база для следующего общего выпуска:

  и SHA256 каждого — `r3-review.json → deployHandoff.baselinePayloadSha256`.

  + 5 evidence-файлов. Маппинг 48 файлов на текущие source paths в JSON; для 5 saved

### Если изменение runtime всё-таки понадобится

Сейчас согласованного нового target-состава нет и обновление не подготовлено,
поскольку достижимое условие advisory не выявлено. Минимальный следующий план при
новых фактах: выбрать исправление только затронутой функции/пакета, проверить
совместимость SDXL+PEFT+CUDA, закрепить полную разрешённую среду и wheels с SHA;
изменить requirements и соответствующие VERSIONS одновременно. Не трактовать
fixed/last_affected из разных advisories как готовый совместимый комплект.

Текущий digest включает code + 9 direct versions + weights/assets/profiles/inventory,
но не Python patch, `+cu128`, ftfy, все transitives, driver/OS. Даже при совпадении
старого digest изменение этих частей не разрешает переносить PASS. Для нового
состава добавить идентификацию environment manifest в deployment identity (или
эквивалентную явную версию состава с проверкой), получить **новый digest**, новый
payload/manifest, не затирая исторические файлы. Локально проверить контракт,
загрузку/совместимость и целостность, затем только в отдельно согласованном владельцем
окне с лимитами рублей, времени и jobs — настоящая qualification по одной генерации
на каждую снова допускаемую пару, review PNG и worker proof. Новый boot также требует
новой qualification. Старые GPU PASS/25 accepted PNG/worker proof автоматически не
переносятся. Никаких платных проверок этим handoff не разрешено.
