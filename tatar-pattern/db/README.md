# PostgreSQL TATAR PATTERN

Актуальная серверная часть — **FastAPI + PostgreSQL**, frontend — **Next.js**.
Старый корневой README с Node/Vite не описывает текущий запуск.
Подробный запуск API и проверенный сценарий: [backend/README.md](../backend/README.md).

## Рабочая БД

Из `Разработка/tatar-pattern/db`:

```bash
cp .env.example .env
# Задайте свой пароль в .env, не публикуйте файл.
docker compose up -d --wait
```

Если БД уже существовала, сохраняйте ее прежние значения окружения и том
`tatar_pattern_pgdata`. Порты доступны только с localhost. Adminer —
[localhost:8080](http://localhost:8080), сервер при входе `db`; остальные значения
берутся из вашего `.env`.

Docker больше не импортирует демонстрационные сиды автоматически. Новая БД
пустая; схема и палитры устанавливаются явным мигратором. Миграции 001–004
сохранены. Добавлены 005 (сессии, признаки fixtures, проверка файлов, журнал
импорта) и 006 (палитры и правила композиции).

Подготовьте `backend/.env` с DATABASE_URL той же БД и Python-окружение по
инструкции backend. Затем из `backend`:

```bash
.venv/bin/python -m scripts.migrate
```

**Перед подключением для обслуживания мигратор вызывает pg_dump** и сохраняет
custom-format копию в `db/backups/` с правами 0600. Если копия не получилась,
операция прекращается. Нужен `pg_dump` версии сервера или новее; для Homebrew
можно задать `PG_BIN=/opt/homebrew/opt/postgresql@16/bin`.

Мигратор применяет все SQL в одной транзакции, фиксирует имя и SHA-256 в
`schema_migrations`, повторный запуск ничего не переигрывает. Для старой БД,
инициализированной Docker, проверяет существование таблиц/служебных колонок
001–004 и записывает их в журнал. Частичная старая схема или измененная уже
примененная миграция останавливает операцию. Все следующие изменения — новым
SQL-файлом. `make reset` отключен. Нельзя использовать `down -v`.

Резервные копии содержат персональные данные и хэши паролей. Они не входят в git.
Копия БД не включает хранилище изображений: `STORAGE_ROOT` нужно сохранять отдельно.
Остановить сервер с сохранением данных: `docker compose stop`.

## Разрешенный каталог

Цепочка: sources → artifacts → artifact_files → elements → element_files.
`approved_element_files` допускает только верифицированный элемент, проверенный
татарский предмет с `usage_scope=рид_и_обучение`, разрешенные права, указанный
источник/основание, исходный кадр, проверенный прозрачный flat_png с SHA-256.
API дополнительно проверяет наличие кадра, PNG и совпадение хэша на диске.

Пять старых сидов маркируются `is_fixture=true`; данные сохраняются. Новый fixture
генерируется отдельной командой и всегда маркируется как тестовый. По умолчанию
API их не показывает. У fixture-генераций явно указаны `TEST_FIXTURE` и
`recipe.isFixture=true`. Они не подтверждают выполнение обязательства 100+.

Непроверенные annotations.csv/annotations.sql не загружать в рабочую БД.
Старый `make import FILE=...` отключен. Разрешена только валидация человеческого
реестра JSON и последующая явная команда импорта, описанная в backend README.
Существующие строки не перезаписываются: несовместимое происхождение, одинаковый
код, путь, SHA-256 или пара предмет/идентичность мотива дают отчет о конфликте.
Ракурсы и перекраски одного мотива должны иметь один `motifIdentity`.

Перед доказательным подсчетом из backend:

```bash
.venv/bin/python -m scripts.catalog_audit --storage-root ./storage --report ./local-test/catalog-audit.json
```

Затем выполните [queries/count_real_elements.sql](queries/count_real_elements.sql)
в SQL-консоли. Запрос исключает fixtures, проверяет происхождение, актуальную
отметку наличия файлов, сворачивает одинаковые SHA-256 и одинаковые идентичности
мотива одного предмета. PostgreSQL не читает локальные изображения сам: подсчет
относится к моменту последнего аудита, указанному в `file_checked_at`. После
перемещения/изменения файлов аудит надо повторить. Смысловую уникальность мотивов
и корректность происхождения подтверждает человек.

## Чистая тестовая PostgreSQL

```bash
docker compose -p tatar-backend-check -f docker-compose.test.yml up -d --wait
```

Это отдельный контейнер, localhost:55432, БД `tatar_pattern_backend_test`, данные
в tmpfs, без рабочего тома. Синтетические данные исчезнут при остановке контейнера.
Тесты создают отдельную схему на каждый запуск и требуют явный
`TP_TEST_DATABASE_URL`, заканчивающийся именем БД `_test`. Инструкция запуска
pytest — в backend README. Существующая рабочая БД для тестов не используется.

## 08.10.2026: локальный реальный каталог

Миграции 007–009 разделяют приемку качества владельцем/локальное использование
и экспертное происхождение/права; добавляют устойчивые ai_jobs и nullable
progress при отсутствии процента облака. Старые 001–006 не изменены.
Импортный пакет только backend/catalog-input, 110 flat/110 texture = 110 мотивов.
SQL count_real_elements исключает fixtures и сворачивает SHA/исходные области;
это доказательство файлов/traceability, не экспертного культурного заключения.
Перед аудитом/импортом задавать TP_ENVIRONMENT=local_project/isolated_test и
loopback DB. Команды и бэкапы — backend/README.md; reset/удаления volume нет.
